# Raahi Learning V1.3 — AI Builder v2 Side-Effects Matrix Audit

Status: **RETROFIT AUDIT COMPLETE — SIDE-EFFECT DECISIONS FROZEN; IMPLEMENTATION GAPS QUEUED BY VERTICAL SLICE.**

Purpose: make notifications, audit/history, Storage, deep-link destinations, expiry behavior and failure semantics explicit for consequential V1.3 transitions. This is an execution-completeness audit, not a product-domain redesign.

## 1. Side-effect invariants

1. The committed PostgreSQL business transition remains authoritative; notification delivery failure must not roll it back.
2. Notifications never grant authority. Opening a notification must route into an ordinary projection/RPC that rechecks current authorization.
3. Private message bodies are not copied into notification bodies.
4. Sponsored/promotional viewer push remains prohibited.
5. One user action should create one attention signal per intended recipient/context unless multiple signals have distinct business meaning.
6. A business record may serve as durable history when it already records actor/time/outcome. Otherwise consequential changes need an audit/history record.
7. Safety evidence/reasons are not leaked through ordinary notifications.
8. Expiry correctness must not depend on a browser timer or notification job.
9. File/Storage authorization remains relationship-based and independent from notification URLs.

## 3. Deep-link policy

Notification payloads already carry sufficient identifiers for the currently wired Enquiry, Class Invitation, Class message, Activity and Test events. The frontend must add one centralized notification-destination resolver.

Rules:

- map known `notification_type` + payload to a canonical route/context;
- mark-read is independent from navigation success;
- never trust payload as authority;
- route open refetches through ordinary authorized projection;
- if relationship/access disappeared, show a safe unavailable state rather than stale private content;
- unknown notification types stay readable but have no action.

This closes the R2 notification-navigation finding without adding a new backend authority model.

## 4. Audit/history policy

Do not add audit rows mechanically to every mutation. A separate audit event is required when the business row does not itself preserve the acting Account/time/outcome and the action is consequential enough to need later explanation.

Required new audit coverage from this pass:

- Trial reschedule/cancel;
- Class Session schedule/cancel;
- learner-side Class leave;
- Class activation lifecycle transition.

Existing row-level actor/time history is sufficient for messages, posts/comments, submissions/reviews and report resolution. Existing explicit audit remains authoritative for Enquiry decisions, Class Invitation acceptance, transfers/removals/completion, organization capability/member changes, Test answer-key correction, Ads governance and other already-audited high-consequence actions.

## 5. Expiry/background-job decision

The DEV database currently has no `cron.job` relation. V1 correctness does not require a background scheduler for the audited invitation/hold expiry rules because canonical commands/read helpers re-evaluate time/current state at execution.

V1 decision:

- no notification merely because an invitation expires;
- do not add pg_cron solely to send expiry messages;
- background cleanup/housekeeping may be added later if operational measurements justify it;
- stale UI must never override execution-time expiry checks.

## 6. Side-effect gaps classified

All current findings are **integration/implementation completeness gaps**, not domain defects:

- `SE-01` Enquiry decline/close counterpart notification.
- `SE-02` Trial schedule/reschedule/cancel notification; audit on reschedule/cancel.
- `SE-03` Class Session schedule/cancel notification + audit.
- `SE-04` attention-worthy Class post notification rules.
- `SE-05` major Class Membership/Class lifecycle notifications; audit for leave/activation.
- `SE-06` Activity submission/review notifications.
- `SE-07` released Test result correction notification.
- `SE-08` Organization capability/removal notification to affected member.

No new entity, relationship, authority rule, Class state, Enquiry state, Test state, Ads state or Storage model is required.

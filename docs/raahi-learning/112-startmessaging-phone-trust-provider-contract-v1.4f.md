# Raahi Learning — StartMessaging Phone Trust Provider Contract V1.4F

Status: **IMPLEMENTATION CONTRACT — PROVIDER PROOF BEFORE ENFORCEMENT**

## 1. Provider evidence

On 2026-09-22 the StartMessaging production account passed KYC and a real sandbox OTP send succeeded with:
- HTTP/application status 201;
- provider status `sent`;
- a provider OTP request ID;
- a provider message ID.

Provider documentation in the authenticated dashboard states:
- base URL: `https://api.startmessaging.com`;
- API authentication header: `X-API-Key`;
- send endpoint: `POST /otp/send`;
- required send data: E.164 `phoneNumber` and variables containing an `otp` generated by the caller;
- status endpoint: `GET /messages/:id`.

StartMessaging therefore acts as OTP **delivery**, not Raahi authorization and not the durable trust source.

## 2. Frozen identity/trust model

The V1.3 trust model remains unchanged:

**Google authenticates the Account. Phone OTP proves control of a phone for trust-sensitive actions. Raahi server relationships/capabilities determine authority.**

StartMessaging must not:
- become the normal login method;
- create a second Raahi Account;
- grant Teacher/Learner/Organization/Admin authority;
- expose its API key to browser code;
- make safety/reporting actions require OTP.

Supabase Auth remains the durable holder of the confirmed phone and `phone_confirmed_at`.
The existing 90-day trust projection remains the source of `fresh/stale/unverified`.

## 3. OTP ownership

Unlike MessageCentral VerifyNow, StartMessaging expects the caller to generate the OTP.

Raahi therefore generates a cryptographically random six-digit code **inside the authenticated Supabase Edge Function**.

The OTP plaintext:
- exists only in Edge Function memory long enough to call StartMessaging;
- is never returned to the browser;
- is never logged;
- is never stored in PostgreSQL;
- is never committed to Git.

The challenge ledger stores only a keyed HMAC-SHA-256 digest bound to:
- provider;
- challenge UUID;
- normalized phone;
- OTP code.

The HMAC key is derived server-side from the Supabase service-role secret with a domain-separated message. No extra browser-visible secret is introduced.

## 4. Send flow

1. Require a valid Supabase user JWT.
2. Resolve the current Auth user server-side.
3. If trust is already fresh and no new phone is being attached, reject as already fresh.
4. For first attach, require a valid Indian E.164 phone.
5. For stale re-proof, use the already confirmed Auth phone.
6. Enforce existing per-user/per-phone send limits.
7. Reuse a just-created active challenge for 15 seconds rather than sending duplicates.
8. Expire older active challenges for that user.
9. Generate a uniform random six-digit OTP in Edge Function memory.
10. Compute keyed digest.
11. Call StartMessaging `POST /otp/send` with:
    - `phoneNumber`;
    - optional configured `templateId`;
    - `variables.otp`;
    - `variables.appName = "Raahi Learning"`.
12. Only after provider acceptance, persist the server-only challenge with:
    - provider = `startmessaging`;
    - provider message ID;
    - keyed digest;
    - 5-minute local expiry.
13. Return only challenge ID, masked phone, expiry, provider and reuse flag to the browser.

## 5. Verify flow

1. Require valid user JWT.
2. Challenge must belong to the current Auth user and provider `startmessaging`.
3. Challenge must be active and unexpired.
4. Maximum 5 verification attempts.
5. Recompute keyed digest from submitted code and compare in constant-time style.
6. On mismatch, increment attempts; fail/lock after the maximum.
7. On match, call Supabase Admin Auth for the **same Auth user ID**:
   - set the challenge phone;
   - set `phone_confirm: true`.
8. Verify postconditions:
   - returned Auth user ID equals initiating Auth user ID;
   - confirmed phone equals challenge phone;
   - `phone_confirmed_at` exists.
9. Mark challenge verified.
10. Browser re-reads `get_my_phone_trust()` and requires `fresh`.
11. Original trust-sensitive canonical command is retried and revalidates all current business state.

## 6. Rate and abuse controls

Retain the existing limits:
- 3 sends/account/10 minutes;
- 10 sends/account/day;
- 5 sends/phone/10 minutes;
- 5 verification attempts/challenge.

Provider errors map to safe public codes:
- invalid/missing API key -> provider auth failure;
- insufficient provider balance -> provider balance failure;
- provider rate limit -> provider limit;
- other provider send failure -> generic OTP send failure.

No provider raw response or API key is returned to browser clients.

## 7. Secret handling

Production secret name:

`STARTMESSAGING_API_KEY`

Optional:

`STARTMESSAGING_TEMPLATE_ID`

The API key must exist only in Supabase Edge Function secrets / server environment.
Never:
- commit it;
- paste it into app JS;
- place it in Cloudflare public variables;
- store it in application tables;
- expose it in build-meta.

## 8. Activation gate

Do **not** switch production from `controlled_pilot_google_only` to enforced phone trust merely because the provider sandbox worked.

Activation requires:
1. migration applied;
2. StartMessaging Edge Function deployed with JWT verification;
3. API secret configured server-side;
4. real authenticated Raahi Account first-attach proof;
5. OTP receipt + verify proof;
6. same Auth user before/after;
7. same Raahi Account before/after;
8. `get_my_phone_trust()` becomes `fresh`;
9. logout -> Google login returns same Auth user/Account;
10. one preserved trust-sensitive action resumes successfully;
11. no synthetic/test residue.

Only then may the runtime phone-trust policy and release config be changed from controlled-pilot bypass to `phone_trust_required + startmessaging`.

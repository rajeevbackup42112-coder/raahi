# Raahi Learning V1.3 — UI ↔ DB Reconciliation

Status: **READ-ONLY RECONCILIATION COMPLETE.** No Supabase migration or Auth-provider configuration was applied while producing this document.

Purpose: map the consolidated V1.3 UX to the actually deployed DEV contract and isolate the smallest required backend/auth delta. This document intentionally does not reopen the frozen Learner/Class/Enquiry/Test/Ads domain.

## Executive result

The deployed V1.2 backend remains a valid base for V1.3.

Most V1.3 UX changes are either:

- presentation only; or
- orchestration over canonical RPCs that already exist.

The remaining backend work is narrow and explicit:

1. durable Account phone-trust freshness + server-verifiable confirmation/gates;
2. private Learner self-access invitation infrastructure;
3. private Organization staff invitation infrastructure;
4. narrow eligible-responsible-teacher read projection for Organization Class setup;
5. unified authorized conversation-list projection;
6. domain-triggered notification production/deep-link contract;
7. optional safe Google-avatar import orchestration over existing profile-public Storage.

There is no evidence for rebuilding Account/Learner, Enquiry, Class Membership, Test, Community, Location or Ads state models.

## 1. Google-primary sign-in

### Existing support

Supabase Auth supports Google OAuth/social sign-in. Raahi already binds application Account identity to `auth.uid()` through `accounts.auth_user_id` and `bootstrap_account`.

The existing Account model stores:

- `display_name`;
- `avatar_type`;
- `avatar_ref`;
- lifecycle status.

`update_account_profile(display_name, avatar_type, avatar_ref, idempotency_key)` already provides the canonical profile mutation.

### V1.3 implication

No new Raahi role/entity is needed for Google.

Frontend/Auth orchestration must:

1. initiate Google Auth;
2. return to/resume the intended Raahi action;
3. bootstrap/find the Account;
4. propose Google name as an editable default;
5. never treat Google metadata as authorization.

### External boundary

Actual Google Cloud OAuth credentials and Supabase Google-provider configuration remain external configuration. They are not database migrations.

## 2. Google profile photo

### Existing support

`register_file_asset(..., purpose_code='profile_public', ...)` maps to the existing `public-profile-media` bucket.

`update_account_profile` accepts `avatar_type='upload'` plus a Raahi avatar reference.

### V1.3 implication

If the user elects to use the Google photo, Raahi should explicitly import/copy the image into Raahi-controlled profile media and then update the Account avatar through the canonical profile command.

Do not persist an external Google avatar URL as permanent authoritative Raahi media and do not auto-publish the image.

### Classification

Existing schema + Storage/RPC orchestration. No domain change.

## 3. First-use intent and learner setup

### Existing support

`create_learner(display_name, access_type, avatar_type, avatar_ref, idempotency_key)` already supports:

- self Learner via `access_type='self'`;
- managed Learner via `access_type='manage'`.

`get_my_account_context()` already returns current active Learner accesses with:

- access id/type;
- Learner id;
- display name;
- avatar type/reference.

It also returns Account capabilities, Organization memberships/capabilities, Location context and manager scopes.

### V1.3 implication

The redesigned `Me · Rahul · Ananya · + Add learner` UX can be populated entirely from authorized server context.

First-use intent does not need a new role table or state machine. It invokes the existing canonical setup command(s) and then refreshes `get_my_account_context()`.

### Classification

Frontend orchestration only.

## 6. Organization responsible-teacher picker

### Existing support and discovered mismatch

`get_organization_members(organization_id)` returns member Account id/display name/status/capabilities, but its read authorization requires `manage_members` (or platform admin).

Class creation, however, is authorized by `manage_classes`, and the existing `create_class` command requires a responsible Teacher Account that is an eligible active Organization member.

Therefore a legitimate Organization member with `manage_classes` but without `manage_members` may be allowed to create a Class while being unable to populate the current all-members projection.

### Required V1.3 addition

Do **not** broaden `get_organization_members` merely for the picker.

Add a narrow projection such as:

`get_eligible_organization_class_teachers(p_organization_id uuid)`

Characteristics:

- callable only when current actor may manage Classes for that Organization (or platform admin);
- returns only fields needed for responsible-teacher choice, e.g. Account id + display name;
- returns only active Organization members satisfying the existing responsible-teacher eligibility rule;
- does not reveal unrelated member-management metadata/capabilities.

### Classification

Small read-projection extension; no relationship change.

## 7. Learner self-access later

### Existing support

`grant_learner_self_access(learner_id, target_account_id, idempotency_key)` already enforces the actual relationship transition and protects invariants including one active self access and separation from the active managing Account.

The missing piece is human-safe target resolution: the existing command expects a target Raahi Account UUID.

### Required V1.3 addition

Add a private, expiring, one-time Learner self-access invitation capability.

Recommended shape:

- invitation id/token hash;
- Learner id;
- issued-by Account;
- state (`active`, `accepted`, `revoked`, `expired` or equivalent);
- expiry/accepted/revoked timestamps;
- plaintext token returned once and never persisted;
- atomic acceptance resolves the current authenticated Account and invokes/preserves the existing self-access invariants;
- replay-safe/idempotent;
- no public Account or Learner search.

The invitation is enabling infrastructure for an already-approved relationship, not a new relationship type.

## 8. Existing learner share to teacher

### Existing support

Current `learner_share_codes` implementation is already strong:

- high-entropy bearer token;
- only hash persisted;
- one active code per Learner;
- finite TTL;
- one-time consume;
- no public resolve/search path;
- atomic integration with `send_class_invitation_with_share_code` and Class capacity rules.

### V1.3 implication

Render the existing token as a WhatsApp-friendly Raahi URL. The server still consumes the same private bearer value; possession never creates Class Membership by itself.

### Classification

Presentation/routing only. No schema/domain change.

## 9. Organization staff invitation

### Existing support

`add_organization_member(organization_id, target_account_id, idempotency_key)` already performs the membership mutation once a target Account is known.

The current human gap is again target resolution: no public Account directory exists or should be added.

### Required V1.3 addition

Add a private, expiring, one-time Organization member invitation capability.

Recommended properties:

- Organization id;
- invited-by Account;
- intended capability preset/set stored server-side or safely snapshotted;
- hashed bearer token, plaintext returned once;
- expiry/revoke/accept lifecycle;
- accepting Account is derived from the authenticated session;
- acceptance atomically creates the member and intended capabilities or safely detects existing membership;
- issuer must retain current `manage_members` authority at execution time;
- recipient acceptance should also recheck Organization status/current restrictions;
- no public Account search/UUID entry.

### Classification

Enabling infrastructure over the existing Organization membership/capability domain.

## 10. Unified Messages inbox

### Existing support

Existing detailed reads/writes are safe and contextual:

- `get_my_enquiries`;
- `get_enquiry_thread`;
- `send_enquiry_message`;
- `get_my_classes`;
- `get_class_learner_thread`;
- `send_class_learner_message`.

`get_class_learner_thread` correctly derives authorization from the current Class + Learner relationship even when no physical thread exists yet.

### Discovered gap

There is no deployed conversation-list projection.

`get_my_enquiries` can list Enquiry contexts but not a unified Class-thread inbox.

`get_my_classes` returns Learner context for learner-side rows, but provider-side rows intentionally have no Learner id. Therefore a Teacher/Organization cannot build a complete authorized Class-conversation inbox from that projection alone without N+1 management reads and client-side reconstruction.

### Required V1.3 addition

Add a narrow projection such as:

`get_my_conversations()`

Return normalized conversation summaries only for currently authorized contexts, for example:

- `conversation_kind` = `enquiry` / `class_learner`;
- context ids (`enquiry_id` or `class_id` + `learner_id`);
- safe display title/context names;
- last message timestamp/safe preview if policy permits;
- unread count later only if evidence requires it.

Opening a row still calls the existing thread projection, which rechecks current authorization. The list projection must not itself create messaging permission.

### Classification

Small read projection; no messaging-domain change.

## 11. Notifications

### Existing support

The deployed notification model already contains:

- recipient Account;
- optional Learner context;
- notification type;
- source type/id;
- title/body;
- payload;
- read/delivery timestamps.

`get_my_notifications(limit)` already returns these fields.

`app_private.enqueue_notification(...)` already validates recipient and Learner-context access and prohibits Sponsored/promotion viewer push patterns.

### Discovered gap

Read-only inspection of deployed function bodies found **no domain function calling `enqueue_notification()`**.

Therefore the notification center is structurally present but not yet an operational consequence of business transitions.

### Required V1.3 addition

Wire a deliberately small event matrix into canonical transitions, preserving the rule that the core state commits first and notification failure must not own/reverse the transition.

Initial useful events:

- Enquiry received / engaged / relevant reply;
- Class Invitation created/resolved where appropriate;
- important Session reschedule/change;
- Activity changes requested/reviewed where useful;
- Test available/result released;
- contextual Class message;
- Organization staff invitation;
- appropriate safety/admin resolution.

Every notification should carry enough source/context data to route to an exact authorized screen. The destination must recheck current authorization at open time.

Sponsored viewer push remains prohibited.

### Classification

Existing table/helper/read; missing transition wiring.

## 12. Phone trust

### Existing support

The current `accounts` table does not have a phone-trust freshness column. Supabase Auth owns current phone/confirmation state.

Current Account columns are only:

- id/auth_user_id;
- display name/avatar;
- lifecycle status;
- timestamps.

### Required V1.3 addition

Add application trust freshness such as:

`accounts.phone_trust_verified_at timestamptz null`

plus private helpers/read projection fields and a narrowly scoped confirmation command/server seam as defined in `41-authentication-phone-trust-v1.3.md`.

Freshness must compare against current Auth phone confirmation/change and 90-day age. Client-supplied timestamps/booleans are never trusted.

### Important unresolved implementation experiment

Before finalizing the migration/command design, DEV must prove whether the chosen standard Supabase phone-verification/reauthentication flow yields trustworthy recent OTP evidence that Postgres can validate for the same Google-authenticated user/session.

If yes, a narrow canonical confirmation command can stamp server `now()` after validating that evidence.

If not, use the smallest Auth-aware server/Edge verification seam. Do not use paid Advanced Phone MFA merely for this policy and do not add a frontend OTP bypass.

### Auth identity caution

Standard Supabase phone attachment can create a phone Auth identity. V1.3 UI must not expose that as a general phone-login fallback unless separately approved.

Also account for the documented `phone_change` stale-attempt ambiguity if `updateUser({phone})` is used: cleanup/uniqueness handling belongs in the implementation plan.

## 13. Account closure checklist

### Existing support

Canonical Account closure already has server-side blockers.

### V1.3 implication

The frontend can translate returned blocker codes into human resolution steps. A dedicated read-only closure-readiness projection may be added only if the current close command does not expose enough preflight detail for good UX.

This is optional and should not duplicate closure truth in the client.

## 14. Enquiry / Trial / Learning Request recovery

Presentation/orchestration only.

## 17. Required acceptance additions

1. New Google Auth session bootstraps/finds exactly one Raahi Account; no capability is inferred from Google.
2. Editable Google name does not later get silently overwritten.
3. Google photo is never public until explicit import/selection.
4. New self/managed Learner onboarding uses `create_learner` once and refreshes account context.
5. Organization Class picker only exposes eligible current responsible teachers to actors who may manage Classes.
6. Learner self-access invite resolves to current authenticated Account, preserves same Learner/history and is one-time/expiring.
7. Organization staff invite is one-time/expiring/revocable and cannot grant beyond the issuer's current authority.
8. Unified conversation list never creates access; opening still rechecks Enquiry/Class authorization.
9. Provider-side Class conversations appear without exposing unrelated Learners/classes.
10. Notification transition failure cannot roll back core state.
11. Notification deep link fails safely if authorization is gone.
12. Stale phone trust blocks only the frozen trust-sensitive action matrix, not existing learning/safety actions.
13. Client cannot forge phone freshness.
14. Phone change invalidates prior freshness.
15. Existing guardian/Test, capacity, Storage and Ads regression suites remain green.

## 18. Next implementation gate

Before applying any V1.3 migration:

1. prove the standard DEV phone verification/reauthentication evidence path using a synthetic Auth user + fixed test OTP;
2. write exact SQL/API contracts for C/E additions;
3. add Given/When/Then DB tests for each new invariant;
4. review impact in order: rules → entities → relationships → states → permissions → UI → tests;
5. then apply the minimal migration to DEV and rerun the full regression suite.
